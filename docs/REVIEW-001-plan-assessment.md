## Part 1 — 평가 계획 (먼저 세운 기준)

### 1.1 평가 방법

문서를 "좋다/나쁘다"로 보지 않고, **세 종류의 오류만** 찾는다. 기획 단계에서 발견 가능한 오류는 이 셋뿐이기 때문이다.

| 오류 유형 | 정의 | 탐지 방법 |
|---|---|---|
| **모순** | 두 문서가 서로 다른 것을 말한다 | 모든 교차 참조를 양방향으로 대조 |
| **누락** | 구현 시 반드시 부딪히는데 어디에도 없다 | 각 블록을 "내가 지금 이걸 만든다면"으로 시뮬레이션 |
| **자기기만** | 문서가 해결했다고 주장하지만 실제로는 안 된 것 | 각 주장에 대해 "그래서 실패 시나리오가 실제로 막히나?" 를 되물음 |

산술이 등장하는 모든 곳(메모리 예산, 비용 모델)은 **직접 재계산**한다.

### 2.2 한 줄 결론

**이 문서 세트는 상위 10% 수준의 기획이다. 다만 "구현 준비 완료" 상태는 아니다.**

## Part 3 — 잘 된 것 (유지할 것)

이 항목들은 개선안에서 건드리지 않는다.

1. **PRD-000 §6 → DATA-001 `collection_runs` → REQ-001 NFR-6/FR-12 → ADR-007 publishing status.** 하나의 실패 모드가 문제정의·스키마·요구사항·인증 결정까지 인과로 이어진다. 대부분의 개인 프로젝트 문서는 이 연결이 없다.
2. **FR-11 / `usage_events` 테이블.** "지표를 측정하려면 시스템이 기록해야 한다"를 v1 요구사항으로 못 박은 것. 사후에 붙이면 절대 안 붙는 종류의 것이다.
3. **ADR-004의 3개 예외 + "손으로 만들었다면 무엇을 했을지" 필수 조항.** 원칙이 교조가 되는 것을 구조적으로 막는다. `## Boundary note`(SQLAlchemy는 DP-1 적용 대상 아님)까지 있는 건 훌륭하다.
4. **ADR-010의 통찰**: "이 프로젝트의 최악은 예외가 아니라 조용히 틀린 데이터다 → 그래서 mock이 아니라 실제 PostgreSQL." 테스트 전략을 취향이 아니라 위험 분석에서 도출했다.
5. **B5의 게이트 조건**: "EC2 비용을 내기 전에 로컬에서 실제 메모리를 측정한다." 되돌릴 수 없는 지출 앞에 검증 게이트를 놓은 것. 이 발상을 다른 곳에도 복제해야 한다(개선안 I-9).
6. **ADR-003 / DATA-001의 한국어 전문검색 자백.** "구조는 공짜지만 검색 품질은 공짜가 아니다"를 스스로 적어둔 것. 나중에 자기 문서에 속지 않게 된다.

#### C-1. 메모리 예산이 산술적으로 성립하지 않는다 — B12는 현재 설계에서 실행 불가

**근거**: `ARCH-001` 메모리 예산표, `BLOCKS-001` B12, `OPS-001` 모니터링 절, `ADR-008` Flux 선택 근거.

ARCH-001의 표를 그대로 합산하면:

| 항목 | 문서상 값 |
|---|---|
| k3s (server, containerd, kubelet) | 500–800 |
| PostgreSQL | 150–300 |
| FastAPI | 80–150 |
| Next.js | 100–200 |
| ingress-nginx | 50–100 |
| Flux | 100–200 |
| **문서 합계** | **980–1,750 MiB** |

여기에 표에서 **빠진 것**들이 있다:

| 누락 항목 | 실측 대략 |
|---|---|
| Ubuntu 24.04 OS 자체 (k3s 제외) | 150–250 |
| cert-manager (controller/webhook/cainjector 3개 pod) | 60–120 |
| collector CronJob pod (실행 중) | 80–150 |
| **B12 관측성 스택** (Prometheus + Grafana + node-exporter + kube-state-metrics) | **350–550** |

t4g.small = 2,048 MiB, 커널/펌웨어 예약 후 가용 약 1,950 MiB.

- B12 **이전**(B9~B11) 상한: 1,750 + 250 + 120 + 150 = **약 2,270 MiB → 이미 초과**
- 하한으로 잡아도 980 + 150 + 60 + 80 = 1,270 MiB. 즉 **하한에서만 겨우 돌아가고, 상한에서는 못 돈다.**
- B12를 얹으면 어떤 시나리오에서도 안 들어간다.

**왜 심각한가**: BLOCKS-001은 B12를 "visible result가 있는 확정 블록"으로 약속했다. OPS-001은 "메모리 예산에 따름(subject to)"이라는 도피 문구만 달아뒀다. 즉 **로드맵은 약속했고 아키텍처는 조건부로 회피했다.** 둘 중 하나는 지금 틀렸다. 그리고 B12는 SRE 포트폴리오에서 **가장 값어치 있는 블록**이다 — 이걸 못 하면 학습 목표 쪽 손실이 크다.

**추가로**: ARCH-001은 "swap을 안전망으로 켠다"고 썼는데, kubelet은 기본적으로 swap이 켜져 있으면 기동을 거부한다(`failSwapOn`). k3s에서 swap을 쓰려면 명시적 설정이 필요하고, PostgreSQL이 swap으로 밀리면 지연이 수십 배가 된다. "안전망"이라는 한 줄로 넘어갈 항목이 아니다.

**수정안**:
1. ARCH-001 메모리표를 **버전 관리되는 원장(ledger)** 으로 바꾼다. 컬럼: 컴포넌트 / requests / limits / 실측값 / 측정일 / 측정 블록. 추정치와 실측치를 구분해서 적는다.
2. 누락 4개 항목(OS, cert-manager, collector, 관측성)을 표에 추가한다.
3. **B12 관측성 방식을 지금 결정한다** → 신규 `ADR-011`. 선택지:
   - (a) Prometheus 대신 **VictoriaMetrics single-node** (약 50–100 MiB, Prometheus의 1/3) + 짧은 보존(7일)
   - (b) 노드에는 exporter/agent만 두고 **저장·대시보드는 외부 무료 티어**(Grafana Cloud 등)로 — ADR-004와 충돌하므로 "손으로 만들었다면" 문단 필수
   - (c) t4g.medium(4 GiB)로 올리고 **야간 정지 스케줄**로 비용 상쇄 (가용성이 지표가 아니므로 PRD-000 §5와 정합)
   - 권장: **(a) + Grafana는 필요할 때만 띄우는 on-demand**. ADR-004 정신을 지키면서 예산 안에 들어간다.
4. swap은 별도 결정 항목으로 분리. 기본은 **swap 없이, 모든 pod에 limits 설정**. swap은 사고 후 대응책이지 설계 전제가 아니다.

#### C-2. 프로젝트가 스스로 정의한 "최악의 실패 모드"가 실제로는 막히지 않았다

**근거**: `PRD-000` §6, `REQ-001` NFR-6, `DATA-001` `collection_runs`, `OPS-001` 모니터링 절.

설계는 이렇다: 수집 실패 → `collection_runs`에 `FAILED` 기록 → **N회 연속 실패 시** webhook 알림. 그리고 대시보드에 마지막 성공 시각 표시.

여기 구멍이 세 개 있다.

**(1) 가장 나쁜 실패는 기록을 남기지 않는다.**
`collection_runs`는 **시작된 실행만** 기록한다. CronJob이 아예 스케줄되지 않은 경우 — 노드 다운, k3s 죽음, kubelet 이상, CronJob 리소스 삭제, 네임스페이스 사고 — 에는 `FAILED` 행이 **생기지 않는다.** 행이 없으므로 "N회 연속 실패" 조건이 영원히 성립하지 않고, **알림은 절대 오지 않는다.** 대시보드는 어제 데이터를 그대로 보여준다.

이건 PRD-000 §6이 묘사한 시나리오 그 자체다. 문서가 막겠다고 선언한 실패를, 설계가 막지 못한다.

**(2) N이 정의되어 있지 않다.**
NFR-6은 "after N consecutive failures"라고만 쓴다. 수집 주기가 24시간이므로 N=2면 **48시간 이상 침묵한 뒤에야** 알림이 온다. 마감 정보 시스템에서 48시간은 치명적이다. 24시간 주기에서 정답은 **N=1**이다.

**(3) FR-12(마지막 성공 시각 표시)는 사용자가 보러 와야 작동한다.**
그런데 PRD-000이 규정한 사용자의 문제가 바로 "안심하고 안 본다"이다. **사용자의 주의력에 의존하는 안전장치는 이 프로젝트에서 무효다.**

**수정안**:
1. **Dead man's switch 도입** — 수집이 *성공할 때마다* 외부 서비스(healthchecks.io 무료 티어 등)에 ping을 보낸다. 정해진 시간 안에 ping이 안 오면 **외부 시스템이** 알림을 보낸다. 내 시스템이 죽어도 알림은 온다. 무료이고 구현은 HTTP GET 한 줄이다.
   - ADR-004 관점: 외부 의존이지만 **자기 자신을 감시하는 시스템은 자기 죽음을 보고할 수 없다**는 것은 SRE의 기본 원리다. 예외 1(직접 하면 더 큰 위험)에 해당. ADR에 "손으로 만들었다면 = 두 번째 노드 또는 외부 VM에 감시자를 띄우는 것, 즉 비용 2배" 를 적으면 된다.
2. **NFR-6의 N을 1로 확정**하고, 조건을 두 개로 분리:
   - 조건 A: 마지막 실행이 `FAILED` → 즉시 알림
   - 조건 B: **마지막 성공 시각 + (수집주기 × 1.5) 초과** → 즉시 알림 ← 실행 자체가 없는 경우를 잡는다
3. FR-12를 "표시"에서 "**표시 + 임계 초과 시 대시보드 상단 경고 배너**"로 강화. 봐도 못 알아채는 것을 막는다.
4. B12에서 **의도적 장애 실험**으로 검증한다: CronJob을 삭제하고 알림이 오는지 확인. 오지 않으면 이 결함은 안 고쳐진 것이다.

> 이 항목 하나가 이 리뷰에서 가장 중요하다. 나머지는 다 비용/일정 문제지만, 이건 **프로젝트의 존재 이유가 무력화되는 문제**다.

#### C-3. 컨테이너 레지스트리가 어디에도 결정되어 있지 않다

**근거**: `ARCH-001` 다이어그램(레지스트리 없음), `B0-B5-specs` B5(이미지 빌드), `BLOCKS-001` B11(CI/CD + Flux), `OPS-001` "never create" 목록(ECR 언급 없음).

B5에서 이미지를 빌드하고, B9에서 클러스터가 그 이미지를 pull하고, B11에서 Flux가 새 태그를 반영한다. **그런데 이미지가 어디 저장되는지 어느 문서에도 없다.**

이건 단순 누락이 아니라 **비용·보안·안정성 세 축에 동시에 걸린 결정**이다:

| 선택지 | 비용 | 문제 |
|---|---|---|
| Docker Hub (무료) | 0 | 익명 pull rate limit. 노드가 재시작할 때마다 pull → 한도 소진 시 **배포가 무작위로 실패** |
| GHCR (GitHub Container Registry) | 0 (public/private 모두 실질 무료) | GitHub Actions와 통합 자연스러움. **권장** |
| ECR | 스토리지 $0.10/GB·월 + **전송료** | 예산 항목 추가. VPC 엔드포인트 없으면 인터넷 경유 |
| 노드에서 직접 빌드 | 0 | 2 GiB 노드에서 Next.js 빌드 = OOM. 불가 |

**수정안**: `ADR-011`(또는 별도 번호)로 **GHCR 확정**. 근거: GitHub Actions와 같은 자격증명, 무료, rate limit 없음, private 가능. ARCH-001 다이어그램에 레지스트리 박스와 pull 화살표 추가. `imagePullSecret` 관리를 ADR-009 스테이지 표에 추가(B9에서 k8s Secret, B11에서 SOPS).

#### M-1. B0가 미해결 항목 때문에 막혀 있는데, 그 항목은 B15까지 필요 없다

**근거**: `STATUS.md` Open 1번, `B0-B5-specs` B0 작업 3번/수용기준, `BLOCKS-001` B15.

B0의 작업 3번은 "대학교 공지 RSS 엔드포인트 확인"이고, STATUS는 이를 "소유자가 조치해야 할 미해결 항목 1번"으로 올려두었다. 그런데 **RSS를 실제로 쓰는 블록은 B15**다. 12개 블록 뒤다.

즉 **첫 블록의 완료 조건이, 마지막 블록에서야 필요한 정보를 요구한다.** 이건 착수를 막는 순수한 마찰이다.

(덧붙여, "University name — required" 가 미해결로 남아 있는 것 자체가 이상하다. 본인 학교는 본인이 안다. 이 문서 세트가 AI 협업으로 작성되면서 닫히지 않은 항목이 그대로 남은 흔적으로 보인다. 이런 항목이 STATUS에 남아 있으면 재개 시 "뭔가 막혀 있다"는 잘못된 신호를 준다.)

**수정안**: B0 작업 3번과 관련 수용기준을 **B15로 이동**. STATUS Open 1번 삭제. B0의 수용기준은 "메일이 쌓이기 시작한다 + 저장소가 존재한다" 두 개로 축소.

#### M-2. 메일 축적에 걸리는 실제 시간(리드타임)이 로드맵에 모델링되어 있지 않다

**근거**: `B0-B5-specs` B0 수용기준("최소 1건 도착"), B2/B3 테스트 요구, `BLOCKS-001` B13.

B3(분류 규칙)은 발신자 주소 규칙을 만드는 블록인데, **규칙을 만들려면 발신자 샘플이 있어야 한다.** B13(본문 파싱)은 ADR-010이 명시하듯 "실제 메일을 읽기 전에는 명세가 존재하지 않는" 블록이다. 즉 **B3와 B13의 입력은 코드가 아니라 시간이다.**

Wevity/JobKorea 알림은 구독 후 며칠~1주 걸릴 수 있고, 발신자 패턴을 파악하려면 **최소 2~4주치 메일**이 필요하다. 현재 로드맵은 B0 → B1 → B2 → B3를 연속으로 그리고 있어서, B3에 도달했을 때 샘플이 5건뿐일 가능성이 높다.

**수정안**:
1. BLOCKS-001에 **"B0는 즉시 착수하고 백그라운드로 계속 돈다"** 를 명시. B0는 완료되는 블록이 아니라 **시작되는 블록**이다.
2. B3의 수용기준에 **데이터 조건** 추가: "최소 3개 발신자로부터 누적 30건 이상 수집된 상태에서 규칙을 작성한다."
3. B13 앞에도 동일한 조건: "누적 100건 이상."
4. 이 대기 시간 동안 할 일을 명시 → **B5~B7(인프라 블록)을 먼저 진행**할 수 있다. 실제로 인프라 블록은 앱 데이터에 의존하지 않으므로, 로드맵을 **앱 트랙 / 인프라 트랙 2개 레인**으로 재구성하는 것이 맞다. 목표 직무가 SRE이므로 인프라 트랙을 지연시킬 이유도 없다.

#### M-3. `content_hash` 구성이 그 목적과 모순된다

**근거**: `DATA-001` 스키마 주석 `sha256(normalised title + org + url)`, 같은 문서 "Deduplication semantics" 2번, `ADR-003` 3번 sub-decision.

`content_hash`의 **선언된 목적**은 "같은 공고가 서로 다른 소스에서 온 경우를 나중에 측정하기 위해서"다 (Wevity와 Linkareer가 같은 공모전을 알림).

그런데 해시 입력에 **`url`이 들어간다.** 서로 다른 소스에서 온 같은 공고는 **거의 확실히 URL이 다르다** (각자의 추적 파라미터, 각자의 상세 페이지). 따라서 이 해시는 **교차 소스 중복에서 절대 일치하지 않는다.** 목적을 달성할 수 없는 구성이다.

**수정안**: 해시 입력을 `normalise(title) + normalise(org)` 로 축소하고, 가능하면 `due_at`(날짜 단위)을 추가. `url`은 제외. 정규화 규칙(공백/특수문자 제거, 대소문자, 한글 자모 정규화 NFC)을 DATA-001에 명시한다 — 명시하지 않으면 재현 불가능한 해시가 된다.
추가로 `content_hash`를 **NOT NULL**로 잡아둔 것도 검토 필요: title이 비어 있는 메일이 오면 삽입이 막힌다.

#### M-4. `UNCLASSIFIED` 카운트가 오염되어 B14의 판단 근거를 망가뜨린다

**근거**: `DATA-001` `category` 컬럼(`NOT NULL DEFAULT 'UNCLASSIFIED'`), `REQ-001` FR-9, `BLOCKS-001` B14.

B14의 설계는 "`UNCLASSIFIED` 물량이 충분히 쌓이면 AI 분류 도입 여부를 데이터로 판단한다"이다. 좋은 설계다.

문제: `category`는 **모든 item에 적용되는 컬럼**인데, FR-9의 분류는 **뉴스레터에만 해당**한다. `type = JOB`, `CONTEST`, 나중의 `SCHEDULE`, `FILE`, RSS로 들어온 공지 — 이들은 분류 대상이 아닌데도 전부 기본값 `UNCLASSIFIED`로 들어간다.

결과: B14에서 "UNCLASSIFIED가 800건 쌓였다 → AI가 필요하다"는 결론이 나오는데, **그 중 750건은 애초에 분류 대상이 아니었다.** 증거 기반 의사결정이 오염된 증거 위에서 이루어진다.

**수정안** (택1):
- (a) `category`를 nullable로 바꾸고, **분류 시도 대상만** `UNCLASSIFIED`를 부여. `NULL` = 분류 대상 아님.
- (b) `classification_attempted BOOLEAN` 컬럼 추가.
- (c) B14의 지표를 `WHERE type='NEWSLETTER' AND category='UNCLASSIFIED'` 로 명시적으로 한정. 가장 싸다.
- 권장: **(a)** — 스키마가 의미를 정확히 표현하게 된다. 지금 고치면 마이그레이션 비용 0.

#### M-5. Gmail 증분 수집 전략이 없다 — 저장할 자리도 없다

**근거**: `B0-B5-specs` B2 작업 목록, `DATA-001` 전체 스키마.

B2는 "Gmail 메시지 → Item 변환"만 적혀 있고, **"어떤 메시지를 가져올 것인가"** 가 없다. 매 실행마다 전체 메일함을 훑으면:
- Gmail API 쿼터 소모가 선형 증가
- 실행 시간이 계속 늘어남 (2 GiB 노드에서 CronJob이 길어지는 건 위험)
- `ON CONFLICT DO NOTHING`은 중복 삽입은 막지만 **불필요한 fetch는 못 막는다**

Gmail API의 정석은 `users.history.list`(historyId 기반 증분) 또는 최소한 `q=after:<timestamp>` 필터다. 어느 쪽이든 **직전 수집 지점을 저장해야 한다.** 현재 스키마에 그 자리가 없다.

**수정안**:
1. B2 작업에 "증분 수집 전략 결정 및 구현" 추가. v1은 `q=after:` 로 충분(단순, 실패 복구 쉬움). `history.list`는 historyId 만료(약 1주) 시 전체 재동기화 폴백이 필요하므로 v1에는 과하다.
2. 스키마에 상태 저장소 추가 — `collection_runs`에 `cursor TEXT` 컬럼을 넣거나, 별도 `collector_state(key, value, updated_at)` 테이블. 후자가 깔끔하다.
3. 수용기준 추가: "두 번째 실행이 첫 실행보다 fetch한 메시지 수가 적다" — 증분이 실제로 작동하는지 검증.

#### M-6. 비용 모델에 환율 리스크가 없고, 천장 초과 시 행동 규칙이 없다

**근거**: `ARCH-001` 비용 모델(~$22/month ≈ 30,000 KRW), `OPS-001` 예산 알람 절, `REQ-001` NFR-1(hard ceiling).

두 가지 문제.

**(1) 천장은 원화, 비용은 달러.**
$22를 환율 1,300원으로 환산하면 28,600원, 1,450원이면 31,900원이다. **환율만으로 hard ceiling을 넘는다.** 문서 어디에도 환율 가정이 없다. NFR-1을 "hard ceiling"이라고 부르면서 통화 리스크를 다루지 않는 건 모순이다.

**(2) 알람은 통지만 한다고 스스로 인정했는데, 그래서 어떻게 할지가 없다.**
OPS-001은 "$20 알람이 울렸을 땐 이미 $20을 썼다"고 정확히 지적한 뒤, 대책으로 **습관 두 개**(목록에 없는 리소스 안 만들기, 청구 콘솔 확인하기)를 제시한다. 습관은 가드레일이 아니다. ARCH-001은 비용 절감 레버 4개를 **순서까지 정해서** 나열해놨는데, **그 레버를 언제 당기는지가 없다.**

**수정안**:
1. NFR-1을 재정의: **"USD 22/월 이하, 그리고 원화 환산 30,000원 이하. 두 조건 중 하나라도 위반 시 ARCH-001 레버 실행."** 환율 가정(예: 1 USD = 1,400 KRW)을 ARCH-001에 명시하고, 월간 운영 리뷰에서 갱신.
2. **에스컬레이션 사다리**를 OPS-001에 표로 추가:

| 트리거 | 행동 | 기한 |
|---|---|---|
| $1 알람 (첫 달 예상 밖) | 리소스 목록을 ARCH-001과 대조, orphan 확인 | 24시간 내 |
| $5 알람 | 예상 대비 초과분 원인 규명, `docs/incidents/` 기록 | 48시간 내 |
| $20 알람 | **레버 3(야간 정지 스케줄) 즉시 실행** | 당일 |
| 월 마감 초과 | 레버 1(RI) 검토 ADR 작성 | 다음 달 첫 주 |

3. 비용 모델 누락 항목 추가: **컨테이너 레지스트리 전송(C-3), EBS 스냅샷, S3 요청 수, 크레딧 소진일**. 특히 **AWS 크레딧 만료일(계정 생성 +12개월)을 STATUS.md에 날짜로 박아둔다.** 크레딧이 끝나는 순간 월 비용이 0에서 $22로 점프하는데, 그 날짜를 잊으면 그게 곧 사고다.

#### M-7. 백업 주기가 요구사항에서 도출되지 않았다 — 주 1회는 이 프로젝트에 부적합

**근거**: `OPS-001` 백업 절, `SEC-001` SEC-10, `BLOCKS-001` B9, `PRD-000` M-2(놓친 마감 0건).

주 1회 `pg_dump` → 최악의 경우 **6일치 수집 데이터 손실**. 이 시스템의 존재 이유는 "마감을 놓치지 않는 것"이다. **6일치 공고가 사라지면 그 안의 마감은 그대로 놓친다.** 즉 백업 주기가 M-2를 직접 위반할 수 있다.

비용 관점에서 주 1회를 고집할 이유도 없다: 단일 사용자 DB의 dump는 수 MB~수십 MB이고, S3에 매일 올려도 월 $0.01 수준이다.

**수정안**:
- **매일 dump + 7일 보관 + 주간본 4주 보관** (S3 lifecycle rule로 자동 만료). 비용 증가 사실상 0.
- RPO/RTO를 문서에 숫자로 명시: **RPO 24시간, RTO 4시간.** 그러면 B9의 복원 훈련이 "돌려봤다"가 아니라 "RTO 4시간을 만족하는지 측정했다"가 된다 — 포트폴리오 가치가 완전히 달라진다.
- 덧붙여: **`raw` 90일 보관 정책(SEC-6)과 백업의 상호작용**이 정의되어 있지 않다. 90일 전 개인 메일 본문이 S3 백업에는 무기한 남는다. SEC-001의 보관 정책이 백업에서 무효화된다. → 백업 보관 기간을 90일 이하로 제한하거나, dump에서 `raw` 컬럼을 제외한 별도 논리 백업을 뜬다. **개인정보 정책의 실질적 구멍이므로 SEC-001에 명시 필요.**

#### M-8. 단일 노드의 데이터 영속성 구현이 미정 — "EBS-backed PVC"는 두 가지 다른 것을 의미한다

**근거**: `ARCH-001` Phase 2 다이어그램("postgres StatefulSet + PVC on EBS"), `ADR-005` trade-off 표.

k3s에서 PVC를 만드는 방법은 최소 두 가지고, **복구 특성이 완전히 다르다**:

| 구현 | 실제 저장 위치 | 인스턴스 종료 시 |
|---|---|---|
| k3s 기본 `local-path` provisioner | 노드의 **루트 EBS 볼륨** 안 디렉터리 | 인스턴스와 함께 **삭제됨** (기본 설정) |
| `aws-ebs-csi-driver` + 별도 EBS 볼륨 | 독립된 EBS 볼륨 | 볼륨 **생존**, 새 노드에 재연결 가능 |

ARCH-001의 표현("EBS gp3 20 GiB" 한 줄)은 전자로 읽히지만, 다이어그램의 "PVC on EBS"는 후자처럼 들린다. **이게 정해지지 않으면 B9에서 만든 것이 노드 교체를 못 버티는지 아닌지를 모른다.**

ADR-005는 "노드 장애 = 전체 중단, 수용함"이라고 썼는데 — **중단(outage)과 데이터 소실(data loss)은 다르다.** 가용성은 포기했지만 데이터를 포기한다고는 어디에도 안 썼다.

**수정안**:
- ADR로 명시 결정. 권장: **별도 EBS 데이터 볼륨 + local-path를 그 마운트 지점으로 지정**. CSI 드라이버 없이도(=ADR-004 정신에 맞게 수동으로) 노드 교체 시 볼륨 재연결이 가능하고, 학습 가치도 높다(EBS attach/detach, 파일시스템 마운트, fstab).
- ADR-005의 trade-off 표에 "노드 장애 시 **데이터는 보존된다**(별도 볼륨 + 일일 백업)"를 명시적으로 추가.

#### M-9. B6–B12에 스펙이 없다 — 의도와 문서 투자가 반대로 되어 있다

**근거**: `BLOCKS-001` "Weighting note"(인프라 블록에 더 많은 여유), `B0-B5-specs` 제목("Later blocks are specified when reached").

BLOCKS-001은 "목표 직무가 SRE이므로 **인프라 블록에 의도적으로 더 많은 비중**을 둔다"고 선언한다. 그런데 실제 문서 투자는 정반대다:

- **B0–B5 (앱 중심)**: 작업 목록, 수용기준, 필수 테스트까지 완비. 5,862 bytes.
- **B6–B12 (인프라, 커리어 핵심)**: 표에 한 줄씩.

특히 **B6–B7은 되돌릴 수 없는 지출이 시작되는 지점**이다. AWS 계정을 만들고 EC2를 켜는 순간부터 시계가 돈다. 이 프로젝트에서 가장 상세한 수용기준이 필요한 곳은 B4가 아니라 B6이다.

**수정안**: B0 착수와 **병행하여** `B6-B7-specs.md`를 먼저 작성. 최소한 다음이 필요:
- B6: 계정 생성 순서, MFA, IAM 사용자/정책, 예산 알람 3개, **Cost Explorer 활성화 날짜 기록**, 크레딧 만료일 STATUS 기재

### 5.3 M-1 / M-2 측정 방법 보강 (축 B 감점 사유)

현재 설계의 문제: `MANUAL_ENTRY`와 `MISSED_ITEM`은 **사용자가 기억해서 눌러야** 기록된다. 그런데 M-1의 대상은 "손으로 옮기는 마찰"이고, M-2의 대상은 **정의상 사용자가 못 본 것**이다. 못 본 것을 사용자가 기록할 수는 없다. 결과적으로 두 지표 모두 **체계적으로 과소 측정되고, 그게 성공처럼 보인다.**

**보강안 — Shadow Audit (주 1회, 10분)**:
- 원본 사이트(Wevity 등)에서 지난 7일 공고를 **무작위 10건** 뽑는다.
- 각각이 내 `items` 테이블에 있는지 조회한다.
- 없는 건수 = **커버리지 갭**. 이게 M-2의 실제 대리 지표다.
- 결과를 `usage_events`에 `kind='COVERAGE_AUDIT'`로 기록하고, note에 `10건 중 8건 발견` 같은 형태로 남긴다.

이건 SRE 관점에서도 의미가 있다: **"시스템이 자기 자신이 놓친 것을 알 수 있는가"** 라는 질문이고, 답은 보통 "외부 기준과 대조해야만 안다"이다. 면접에서 말할 거리가 된다.

### 5.4 SRE 포트폴리오 강화 (축 G 감점 사유)

WORKFLOW는 "인시던트 기록은 이 저장소에서 가장 가치 있는 산출물"이라고 정확히 짚었다. 그런데 **인시던트를 만들 계획이 없다.** 단일 사용자 시스템에서 자연 발생 장애를 기다리면 몇 달이 걸리고, 그동안 `docs/incidents/`는 비어 있는다.

**GameDay 계획 추가** — 각 블록에 의도적 장애 1개씩, postmortem 필수:

| 블록 | 장애 주입 | 검증하는 것 |
|---|---|---|
| B9 | PostgreSQL pod 강제 삭제 | StatefulSet 재기동, 데이터 보존, 애플리케이션 재연결 |
| B9 | 백업에서 스크래치 DB로 복원 | RTO 실측 (M-7) |
| B10 | EC2 인스턴스 종료 후 Terraform으로 재생성 | 진짜 IaC인지, 데이터 볼륨이 살아남는지 (M-8) |
| B11 | 잘못된 이미지 태그 배포 후 롤백 | Flux 롤백 경로, 배포 안전성 |
| B12 | **CronJob 삭제** | **C-2의 dead man's switch가 실제로 울리는지** |
| B12 | 디스크 90% 채우기 | 디스크 알림, PostgreSQL 동작, 복구 절차 |

각각에 대해 `docs/incidents/YYYY-MM-DD-<slug>.md` 작성: 타임라인, 영향, 탐지 방법, 조치, **재발 방지**. 6개면 SRE 포트폴리오로 충분하다.

**SLO 정의 추가**: PRD-000이 "가용성은 지표가 아니다"라고 한 것은 옳다. 하지만 그 자리를 대체할 지표를 **수치화하지 않았다.** NFR-6("신선도 가시성")을 SLI/SLO 형태로 바꾸면:

> **SLI**: 임의 시점에 `now() - last_successful_collection < 30h` 인가
> **SLO**: 월간 99% (= 월 약 7시간의 error budget)

이렇게 하면 B12의 대시보드/알림이 자연스럽게 **SLO 위반 알림**이 되고, 월간 운영 리뷰에 "error budget 소진율"이라는 항목이 생긴다. SLI/SLO/error budget은 SRE 면접의 단골 주제이고, **직접 정의하고 운영해본 사람은 드물다.** 투자 대비 회수가 가장 큰 개선 항목이다.

## Part 6 — 확인이 필요한 것

내가 판단할 수 없어 남겨두는 항목이다.

1. **B12 관측성 방식** — VictoriaMetrics 자체 운영(a) / 외부 무료 티어(b) / 인스턴스 상향 + 야간 정지(c) 중 어느 쪽인가. (c)는 비용 구조를 바꾸므로 ARCH-001 전면 개정이 필요하다.
2. **데이터 소실 허용 범위** — "노드 장애 = 전체 중단"은 수용했는데, **데이터 소실도 수용하는가?** 아니라면 M-8의 별도 볼륨은 선택이 아니라 필수다.
3. **환율 가정** — NFR-1의 30,000원을 어떤 환율 기준으로 관리할 것인가. 아니면 천장을 USD로 재정의할 것인가.
4. **Dead man's switch의 외부 의존 수용 여부** — ADR-004(DP-1) 위반으로 볼 것인가, 예외 1로 볼 것인가. 내 판단은 예외 1이지만, 이건 원칙의 소유자가 정할 문제다.
5. **STATUS Open 1번(대학 이름)** — 왜 미해결로 남아 있는지. 단순 누락이면 지금 닫으면 된다.
